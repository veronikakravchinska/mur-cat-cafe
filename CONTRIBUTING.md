# Як долучитися до проєкту «Мур»

## Стратегія розгалуження: Git Flow

| Гілка | Звідки створюється | Куди зливається | Призначення |
|---|---|---|---|
| `main` | — | — | лише стабільні релізи, кожен позначений підписаним тегом `vX.Y.Z` |
| `develop` | `main` (один раз) | `main` через `release/*` | інтеграція готових функцій, гілка за замовчуванням |
| `feature/<№ issue>-<опис>` | `develop` | `develop` | нова функціональність |
| `fix/<№ issue>-<опис>` | `develop` | `develop` | виправлення помилки, знайденої до релізу |
| `release/<x.y.z>` | `develop` | `main` і `develop` | підготовка релізу: лише виправлення, версія, changelog |
| `hotfix/<№ issue>-<опис>` | `main` | `main` і `develop` | термінове виправлення в продакшні |

Правила назв гілок:
- лише латиниця в нижньому регістрі, цифри і дефіс: `feature/12-table-booking`;
- номер issue обов'язковий для `feature/`, `fix/`, `hotfix/`;
- версія в `release/` — за SemVer: `release/1.2.0`.

## Процес pull request

1. Створіть issue і запам'ятайте його номер.
2. Створіть гілку за правилами вище: `feature/*` і `fix/*` — від `develop`, `hotfix/*` — від `main`.
3. Відкрийте PR:
   - `feature/*`, `fix/*` → лише в `develop`;
   - `release/*`, `hotfix/*` → у `main`, після злиття — окремий PR із `main` у `develop`, щоб зміни не загубилися.
4. Заповніть шаблон PR і додайте рядок `Closes #<№ issue>`.
5. Потрібне 1 схвалення від власника коду з `.github/CODEOWNERS`; усі коментарі рецензента мають бути закриті (Resolve conversation).
6. Після нових комітів схвалення скасовується — попросіть рецензента переглянути ще раз.
7. Спосіб злиття — лише **Squash and merge**; гілка видаляється автоматично.

Прямий push у `main` і `develop` заборонено, force push і видалення цих гілок — теж.

## Повідомлення комітів: Conventional Commits

Формат: `тип(область): опис` — опис з малої літери, без крапки в кінці, до 72 символів.

Типи:
- `feat` — нова функціональність
- `fix` — виправлення помилки
- `docs` — документація
- `test` — тести
- `refactor` — рефакторинг без зміни поведінки
- `ci` — конвеєр CI/CD
- `chore` — службові зміни
- `sec` — зміни безпеки

Основна область проєкту — `cats`. Приклади:

```
feat(cats): картка кота з характером і станом здоров'я
fix(cats): кіт на відпочинку не показується в бронюванні
sec(cats): перевірка ролі ветеринара перед зміною картки
docs(cats): правила спілкування з котами
```

Заголовок PR — у тому самому форматі, бо при squash він стає повідомленням коміту в `develop`.

## Підпис комітів

Усі коміти підписуються GPG-ключем (`git config commit.gpgsign true`).
Непідписані коміти не можна злити в захищені гілки.
